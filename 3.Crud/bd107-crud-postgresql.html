01

El ciclo CRUD: las cuatro operaciones fundamentales

⏱ 15 min de lectura

CRUD es el acrónimo de las cuatro operaciones básicas sobre los datos: Create (crear), Read (leer), Update (actualizar) y Delete (borrar). Desde la tienda escolar hasta un banco, todo sistema de información se apoya en estas cuatro.

CCreateINSERT
RReadSELECT
UUpdateUPDATE
DDeleteDELETE
OperaciónComandoQué haceQué responde psql
CreateINSERTAgrega filas nuevas a una tabla.INSERT 0 1
ReadSELECTConsulta los datos (lo verás a fondo en BD·108).(5 rows)
UpdateUPDATEModifica filas que ya existen.UPDATE 2
DeleteDELETEElimina filas que ya existen.DELETE 1

Fíjate en la última columna: PostgreSQL te dice cuántas filas tocó cada instrucción. Léelo siempre. Si esperabas UPDATE 1 y ves UPDATE 48, algo salió mal. En INSERT 0 1 el primer número es un resto histórico que siempre vale 0; el segundo son las filas insertadas.

La regla de oro del orden con FK

Cuando las tablas están relacionadas, el orden de las operaciones no es opcional:

OperaciónOrden correctoPor qué
INSERTPrimero el padre, después el hijo.El hijo necesita que exista la PK a la que va a apuntar.
DELETEPrimero el hijo, después el padre.No puedes borrar un padre mientras haya hijos apuntándole (salvo con ON DELETE CASCADE).
💡 Analogía

Construir y demoler una casa: primero los cimientos y luego las paredes (INSERT: padre → hijo). Para demoler, primero las paredes y luego los cimientos (DELETE: hijo → padre). Al revés, todo se derrumba.

Trabajarás sobre tienda_db, con las tablas categorias, productos, clientes, pedidos, detalle_pedido y productos_respaldo. El script completo para crearlas en tu propio PostgreSQL está al final del laboratorio. En el laboratorio ya existen y tienen datos.

02

INSERT: crear datos nuevos

⏱ 25 min de práctica

INSERT simple: una fila a la vez

Nombras la tabla, las columnas que vas a llenar y, en el mismo orden, los valores. Los textos van entre comillas simples.

insert_simple.sql
-- Una categoría nueva (tabla padre)
INSERT INTO categorias (nombre)
VALUES ('Postres');

-- Un producto (tabla hijo) que apunta a la categoría 1, Bebidas
INSERT INTO productos (nombre, categoria_id, precio, cantidad)
VALUES ('Limonada', 1, 2800, 20);
INSERT 0 1 INSERT 0 1

INSERT múltiple: varias filas en una instrucción

insert_multiple.sql
INSERT INTO categorias (nombre)
VALUES ('Lácteos'),
       ('Panadería'),
       ('Frutas');
INSERT 0 3

Omitir columnas con DEFAULT

Si una columna tiene DEFAULT, puedes dejarla fuera y PostgreSQL pone el valor por ti. También puedes escribir la palabra DEFAULT como valor.

insert_default.sql
-- activo tiene DEFAULT TRUE: lo omitimos
INSERT INTO productos (nombre, categoria_id, precio, cantidad)
VALUES ('Pandebono', 2, 1500, 40);

-- cantidad tiene DEFAULT 0: lo pedimos de forma explícita
INSERT INTO productos (nombre, categoria_id, precio, cantidad)
VALUES ('Buñuelo', 2, 1200, DEFAULT)
RETURNING nombre, cantidad, activo;
INSERT 0 1 nombre | cantidad | activo ----------+----------+-------- Buñuelo | 0 | t
🐘 Si vienes de SQL Server: BIT ya no, BOOLEAN sí

En SQL Server activo era BIT y escribías 1 o 0. En PostgreSQL es BOOLEAN: escribe TRUE o FALSE. Si insertas un 1, recibes column "activo" is of type boolean but expression is of type integer. psql muestra los booleanos como t y f.

NULL explícito

Si una columna admite NULL y quieres dejarla vacía a propósito, escribe NULL sin comillas. Con comillas sería el texto “NULL”, que no es lo mismo.

insert_null.sql
INSERT INTO categorias (nombre, descripcion)
VALUES ('Helados', NULL);

El id no se escribe: IDENTITY lo genera

En tienda_db cada id está declarado como INTEGER GENERATED ALWAYS AS IDENTITY. PostgreSQL lo numera solo, y si intentas escribirlo te detiene:

insert_identity.sql
INSERT INTO categorias (id, nombre)
VALUES (10, 'Postres');
ERROR: cannot insert a non-DEFAULT value into column "id" DETAIL: Column "id" is an identity column defined as GENERATED ALWAYS. HINT: Use OVERRIDING SYSTEM VALUE to override.
🐘 SERIAL e IDENTITY

En tutoriales viejos verás id SERIAL PRIMARY KEY. Funciona, pero sí te deja escribir el id a mano y el contador no se entera, así que tarde o temprano chocas con duplicate key value violates unique constraint. GENERATED ALWAYS AS IDENTITY es el estándar actual y te protege de ese error.

Un detalle más: si un INSERT falla, el número que ya se había reservado se pierde. Por eso es normal ver huecos en los id (1, 2, 4…). No es un problema: un id identifica, no cuenta.

RETURNING: el id recién creado, sin otra consulta

Agrega RETURNING al final del INSERT y PostgreSQL te devuelve las columnas que pidas de las filas que acaba de crear. Es la forma de saber qué id le tocó a tu registro para usarlo en la tabla hijo.

insert_returning.sql
INSERT INTO clientes (nombre, telefono)
VALUES ('Valentina Ruiz', '310-111-2222')
RETURNING id, nombre;
id | nombre ----+---------------- 3 | Valentina Ruiz (1 row) INSERT 0 1
🐘 Adiós SCOPE_IDENTITY()

Lo que en SQL Server hacías con SELECT SCOPE_IDENTITY(); o OUTPUT INSERTED.id, en PostgreSQL se hace con RETURNING id. Funciona igual en UPDATE y DELETE.

INSERT con SELECT: copiar datos de otra tabla

insert_select.sql
-- Copiar los productos activos a la tabla de respaldo
INSERT INTO productos_respaldo (nombre, categoria_id, precio, cantidad)
SELECT nombre, categoria_id, precio, cantidad
FROM productos
WHERE activo = TRUE;
INSERT 0 4

Sirve para respaldos, migraciones o para llenar una tabla de resumen con datos que ya existen. Fíjate en que no hay VALUES: las filas vienen del SELECT.

Bonus: ON CONFLICT, insertar sin chocar

categorias.nombre es UNIQUE, así que insertar “Bebidas” otra vez da error. Con ON CONFLICT decides qué hacer cuando la fila ya existe: ignorarla o actualizarla. A esto se le llama upsert.

upsert.sql
-- Si ya existe, no hagas nada
INSERT INTO categorias (nombre)
VALUES ('Bebidas')
ON CONFLICT (nombre) DO NOTHING;

-- Si ya existe, actualiza la descripción con el valor que intenté insertar
INSERT INTO categorias (nombre, descripcion)
VALUES ('Bebidas', 'Frías y calientes')
ON CONFLICT (nombre) DO UPDATE SET descripcion = EXCLUDED.descripcion;
INSERT 0 0 INSERT 0 1

EXCLUDED es la fila que intentaste insertar y fue rechazada por el conflicto.

03

UPDATE: modificar datos existentes

⏱ 25 min de práctica

La sintaxis correcta: siempre con WHERE

update_con_where.sql
-- Subir el precio de la Gaseosa (id = 1)
UPDATE productos
SET precio = 3800
WHERE id = 1;
UPDATE 1

UPDATE con expresiones

El nuevo valor puede calcularse a partir del valor actual de la columna.

update_expresion.sql
-- Aumentar 10 % todos los productos de Fritos (categoría 2)
UPDATE productos
SET precio = precio * 1.10
WHERE categoria_id = 2;
UPDATE 2

Varias columnas a la vez y RETURNING

update_multiple.sql
UPDATE productos
SET precio = 2700,
    cantidad = cantidad - 5
WHERE nombre = 'Empanada'
RETURNING nombre, precio, cantidad;
nombre | precio | cantidad ----------+---------+---------- Empanada | 2700.00 | 25 (1 row) UPDATE 1

Con RETURNING ves de inmediato cómo quedó cada fila modificada.

Borrado lógico: desactivar en vez de borrar

Muchas veces no conviene borrar un producto que ya aparece en pedidos antiguos. En su lugar se marca como inactivo:

borrado_logico.sql
UPDATE productos
SET activo = FALSE
WHERE id = 4;
UPDATE 1

⚠️ El desastre clásico: UPDATE sin WHERE

peligro.sql
-- ⚠️ PELIGRO: afecta TODAS las filas
UPDATE productos
SET precio = 0;
UPDATE 5

Acabas de poner todos los productos a precio cero. No hay error de sintaxis ni advertencia: PostgreSQL ejecuta exactamente lo que le pediste. El problema es que le pediste algo que no querías. Y psql trabaja en modo autocommit: el cambio ya quedó guardado.

🚨 Regla de supervivencia

Antes de un UPDATE, escribe el SELECT con el mismo WHERE y mira qué filas vas a tocar. Si el resultado es el esperado, cambia SELECT * por UPDATE … SET … y conserva el WHERE intacto.

select_primero.sql
-- Paso 1: ¿qué filas se van a modificar?
SELECT * FROM productos WHERE id = 1;

-- Paso 2: si es lo que esperabas, ejecuta el UPDATE con el mismo WHERE
UPDATE productos SET precio = 3800 WHERE id = 1;

En la unidad 06 verás una red de seguridad todavía mejor: abrir una transacción antes de un cambio grande.

04

DELETE y TRUNCATE: eliminar datos

⏱ 20 min de práctica

DELETE con WHERE: borrar filas específicas

delete_con_where.sql
-- Borrar el producto con id = 3 (Café)
DELETE FROM productos
WHERE id = 3;
DELETE 1

También acepta RETURNING, útil para ver qué se borró:

delete_returning.sql
DELETE FROM productos
WHERE cantidad = 0
RETURNING id, nombre;

⚠️ DELETE sin WHERE: vaciar la tabla

peligro_delete.sql
-- ⚠️ PELIGRO: borra TODAS las filas
DELETE FROM detalle_pedido;
DELETE 2

La tabla sigue existiendo, pero sin datos. Y el contador del id no se reinicia: el próximo id sigue desde donde iba.

TRUNCATE: vaciar de golpe

truncate.sql
-- Vacía la tabla, pero el contador del id sigue donde iba
TRUNCATE TABLE productos_respaldo;

-- Vacía la tabla y reinicia el contador a 1
TRUNCATE TABLE productos_respaldo RESTART IDENTITY;
TRUNCATE TABLE TRUNCATE TABLE
🐘 Diferencia importante con SQL Server

En SQL Server, TRUNCATE TABLE reinicia el IDENTITY. En PostgreSQL no, a menos que agregues RESTART IDENTITY. Y si otra tabla tiene una FK que apunta a la que quieres vaciar, PostgreSQL se niega aunque esa otra tabla esté vacía; con CASCADE vacía también todas las tablas que dependen de ella. Úsalo con muchísimo cuidado.

truncate_fk.sql
TRUNCATE TABLE categorias;
ERROR: cannot truncate a table referenced in a foreign key constraint DETAIL: Table "productos" references "categorias". HINT: Truncate table "productos" at the same time, or use TRUNCATE ... CASCADE.
CaracterísticaDELETE FROM tablaTRUNCATE TABLE tabla
¿Se puede filtrar con WHERE?SíNo, vacía todo
¿Reinicia el contador del id?NoSolo con RESTART IDENTITY
¿Qué pasa con las FK?Falla si hay hijos que apuntan a las filas borradasFalla si alguna tabla le apunta, salvo con CASCADE
¿Admite RETURNING?SíNo
¿Se puede deshacer?Sí, dentro de una transacciónSí, dentro de una transacción
VelocidadFila por fila, más lento en tablas grandesMuy rápido, libera el espacio de inmediato
🚨 La misma regla de supervivencia

Antes de un DELETE, ejecuta el SELECT con el mismo WHERE para ver exactamente qué filas se van a borrar.

05

El orden con FK: INSERT padre → hijo, DELETE hijo → padre

⏱ 15 min de práctica

INSERT: primero el padre

Intentemos insertar un producto en una categoría que no existe:

fk_insert.sql
-- ⚠️ La categoría 999 no existe
INSERT INTO productos (nombre, categoria_id, precio, cantidad)
VALUES ('Producto fantasma', 999, 1000, 5);
ERROR: insert or update on table "productos" violates foreign key constraint "productos_categoria_id_fkey" DETAIL: Key (categoria_id)=(999) is not present in table "categorias".

La solución: crear primero la categoría y usar el id que te devuelve.

fk_insert_ok.sql
-- ✔ Orden correcto
INSERT INTO categorias (nombre) VALUES ('Saludables') RETURNING id;   -- supón que devuelve 4

INSERT INTO productos (nombre, categoria_id, precio, cantidad)
VALUES ('Ensalada de frutas', 4, 4500, 10);
💡 Sin adivinar el id

Si no quieres depender del número exacto, una subconsulta busca el id por nombre: VALUES ('Ensalada de frutas', (SELECT id FROM categorias WHERE nombre = 'Saludables'), 4500, 10).

DELETE: primero el hijo

Intentemos borrar la categoría Snacks, que todavía tiene productos:

fk_delete.sql
-- ⚠️ Papas fritas apunta a la categoría 3
DELETE FROM categorias WHERE id = 3;
ERROR: update or delete on table "categorias" violates foreign key constraint "productos_categoria_id_fkey" on table "productos" DETAIL: Key (id)=(3) is still referenced from table "productos".
fk_delete_ok.sql
-- ✔ Orden correcto
DELETE FROM productos WHERE categoria_id = 3;   -- primero los hijos
DELETE FROM categorias WHERE id = 3;            -- después el padre
DELETE 1 DELETE 1
🐘 El código del error: 23503

En SQL Server este error era el Msg 547. En PostgreSQL toda violación de llave foránea tiene el código SQLSTATE 23503 (foreign_key_violation). Si tu PostgreSQL está instalado en español verás el mensaje traducido, pero el código es el mismo.

La alternativa: ON DELETE CASCADE

En tienda_db, detalle_pedido.pedido_id se definió con ON DELETE CASCADE: si borras un pedido, PostgreSQL borra sus líneas de detalle automáticamente.

cascade.sql
-- Borra el pedido 1 y, en cascada, sus 2 líneas de detalle
DELETE FROM pedidos WHERE id = 1;
DELETE 1

Observa que psql dice DELETE 1: solo cuenta las filas de la tabla que nombraste, no las que se fueron en cascada. Es cómodo, pero peligroso: asegúrate de que de verdad quieres ese comportamiento antes de definirlo.

06

Transacciones: el botón de deshacer de PostgreSQL

⏱ 20 min de práctica

Una transacción agrupa varias instrucciones en una sola unidad: o se confirman todas, o no se confirma ninguna. Mientras está abierta, psql cambia el prompt de tienda_db=# a tienda_db=*# para recordártelo.

transaccion.sql
BEGIN;

-- Operación 1: el pedido (padre)
INSERT INTO pedidos (cliente_id, total)
VALUES (2, 6000)
RETURNING id;                 -- supón que devuelve 2

-- Operación 2: su detalle (hijo)
INSERT INTO detalle_pedido (pedido_id, producto_id, cantidad, precio_unitario)
VALUES (2, 1, 1, 3500),
       (2, 2, 1, 2500);

-- Todo bien: confirmar
COMMIT;
BEGIN INSERT 0 1 INSERT 0 2 COMMIT
ComandoQué hace
BEGIN;Abre la transacción. Desde aquí los cambios son provisionales y nadie más los ve.
COMMIT;Confirma todos los cambios. Ya no se pueden deshacer.
ROLLBACK;Deshace todo lo hecho desde el BEGIN, como si nunca hubiera pasado.
SAVEPOINT nombre;Marca un punto intermedio dentro de la transacción.
ROLLBACK TO SAVEPOINT nombre;Deshace solo lo posterior a esa marca.
🐘 BEGIN TRAN no existe

En SQL Server escribías BEGIN TRAN. En PostgreSQL es BEGIN; (o BEGIN TRANSACTION;, o START TRANSACTION;). Y sin BEGIN, psql confirma cada instrucción apenas termina: eso es el modo autocommit.

El simulacro de desastre

Con una transacción abierta, hasta un DELETE sin WHERE tiene arreglo:

simulacro.sql
BEGIN;
DELETE FROM detalle_pedido;              -- ¡uy, sin WHERE!
SELECT count(*) FROM detalle_pedido;     -- 0
ROLLBACK;
SELECT count(*) FROM detalle_pedido;     -- 2: todo volvió

Cuando algo falla dentro de la transacción

PostgreSQL es estricto: si una instrucción falla dentro de una transacción, toda la transacción queda abortada. El prompt cambia a tienda_db=!# y cualquier otra instrucción se rechaza hasta que escribas ROLLBACK.

abortada.sql
BEGIN;
INSERT INTO productos (nombre, categoria_id, precio)
VALUES ('Fantasma', 999, 100);            -- falla: la categoría no existe
INSERT INTO categorias (nombre) VALUES ('Postres');   -- rechazada
ROLLBACK;
ERROR: current transaction is aborted, commands ignored until end of transaction block

Si escribes COMMIT sobre una transacción abortada, PostgreSQL responde ROLLBACK: no guarda nada. Esa es justamente la garantía de “todo o nada”.

SAVEPOINT: deshacer solo una parte

savepoint.sql
BEGIN;
UPDATE productos SET precio = 4000 WHERE id = 1;
SAVEPOINT antes_de_borrar;
DELETE FROM productos WHERE id = 3;
ROLLBACK TO SAVEPOINT antes_de_borrar;   -- el Café vuelve, el precio nuevo se queda
COMMIT;
🤓 ¿Cuándo se usa esto?

En operaciones que tocan varias tablas y deben ser atómicas: una venta que crea el pedido, su detalle y descuenta inventario; una transferencia que resta de una cuenta y suma en otra. Si falla un paso, se deshacen todos. Un detalle: los contadores de id no retroceden con ROLLBACK, así que verás un salto en la numeración.

CREATE DATABASE tienda_db;

CREATE TABLE categorias (
  id          INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nombre      VARCHAR(50) NOT NULL UNIQUE,
  descripcion TEXT
);

CREATE TABLE productos (
  id           INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nombre       VARCHAR(80) NOT NULL,
  categoria_id INTEGER NOT NULL REFERENCES categorias (id),
  precio       NUMERIC(10,2) NOT NULL CHECK (precio >= 0),
  cantidad     INTEGER NOT NULL DEFAULT 0 CHECK (cantidad >= 0),
  activo       BOOLEAN NOT NULL DEFAULT TRUE
);

CREATE TABLE clientes (
  id       INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nombre   VARCHAR(80) NOT NULL,
  telefono VARCHAR(20)
);

CREATE TABLE pedidos (
  id         INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  cliente_id INTEGER NOT NULL REFERENCES clientes (id),
  fecha      DATE NOT NULL DEFAULT CURRENT_DATE,
  total      NUMERIC(10,2) NOT NULL DEFAULT 0 CHECK (total >= 0)
);

CREATE TABLE detalle_pedido (
  id              INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  pedido_id       INTEGER NOT NULL REFERENCES pedidos (id) ON DELETE CASCADE,
  producto_id     INTEGER NOT NULL REFERENCES productos (id),
  cantidad        INTEGER NOT NULL CHECK (cantidad > 0),
  precio_unitario NUMERIC(10,2) NOT NULL CHECK (precio_unitario >= 0)
);

CREATE TABLE productos_respaldo (
  id           INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  nombre       VARCHAR(80),
  categoria_id INTEGER,
  precio       NUMERIC(10,2),
  cantidad     INTEGER
);

          Mini glosario
          
  
          
   
          CRUD
          Create, Read, Update, Delete: las cuatro operaciones fundamentales sobre los datos.
          
   
          DML
          Lenguaje de manipulación de datos: INSERT, UPDATE, DELETE y SELECT.
          
   
          RETURNING
          Cláusula de PostgreSQL que devuelve columnas de las filas insertadas, modificadas o borradas.
          
   
          ON CONFLICT
          Indica qué hacer cuando un INSERT choca con una restricción UNIQUE: nada, o actualizar.
          
   
          EXCLUDED
          Dentro de ON CONFLICT DO UPDATE, la fila que intentaste insertar.
          
   
          IDENTITY
          Columna numerada automáticamente. Con GENERATED ALWAYS no se puede escribir a mano.
          
   
          TRUNCATE
          Vacía una tabla completa de golpe. No admite WHERE.
          
   
          RESTART IDENTITY
          Opción de TRUNCATE que reinicia el contador del id a 1.
          
   
          ON DELETE CASCADE
          Opción de una FK: al borrar el padre se borran sus hijos automáticamente.
          
   
          Borrado lógico
          Marcar una fila como inactiva con UPDATE en vez de borrarla con DELETE.
          
   
          Autocommit
          Modo por defecto de psql: cada instrucción se confirma sola si no abriste BEGIN.
          
   
          BEGIN · COMMIT · ROLLBACK
          Abren, confirman y deshacen una transacción.
          
   
          SAVEPOINT
          Punto de guardado dentro de una transacción para deshacer solo una parte.
          
   
          Transacción abortada
          Estado tras un error dentro de BEGIN: todo se rechaza hasta ROLLBACK. psql lo marca con =!#.
          
   
          SQLSTATE 23503
          Código de error de violación de llave foránea.
